# Roadmap and decisions

**Status:** 2026-10-14. "The design" and § numbers refer to `protocol.md`.

## Decisions

| # | Decision | Why |
|---|---|---|
| D1 | **The protocol core owns its routing and table code**; `bark-proto` takes no external routing or mesh dependency. | The design's routing is small and specific: forwarding toward a 7-byte position that is also the relay identity, depth-first search (DFS) around gaps with per-message state in each relay, per-hop acknowledgement (ACK) with demotion. A general mesh library brings network-wide tables, position estimation and node IDs the design leaves out (§12), and pins its own embassy versions. A few hundred lines of our own keep the API shaped by the design alone. |
| D2 | **Simulator first.** Before any firmware, build a discrete-event simulator that places relays and leaves on a grid, takes a sparse pairwise signal-power table (only pairs in range, per channel, varying over time), and runs traffic through the real protocol core. | The design's capacity numbers (§13) are order-of-magnitude estimates with 2× uncertainty on hearing radius and hop count. The thresholds in O3 and the eviction policy in O4 can only be tuned against a model. Boards arrive in three weeks; the simulator is useful now and after. |
| D3 | **The protocol core does no I/O** (`bark-proto`): a state machine driven by `(event, now)` that returns actions; no executor, no async, no radio driver. Firmware wraps it in an embassy task; the simulator drives it from an event queue. | One implementation under test in both places. Thousands of nodes in one process need a core that does not own tasks or channels. Decided 2026-10-14 (Q1). |
| D4 | `lora-phy` from the lora-rs **git main**, not crates.io 3.0.1 (July 2024). | SF5, `get_rssi`, arbitrary sync word, `rx_switch_channel`, duty-cycled receive all landed after 3.0.1. Pin a revision. |
| D5 | BLE via **TrouBLE + nrf-sdc**, not nrf-softdevice. | nrf-softdevice last released January 2024; trouble-host 0.8 and nrf-sdc 0.4 both released August 2026 with GATT, notifications and security. Known to run on a T-Echo. |
| D6 | **Keep the stock bootloader.** Application linked at `0x26000`, flashed as UF2 (family `0xADA52840`, volume `TECHOBOOT`). | The T-Echo ships Adafruit's UF2 bootloader with SoftDevice S140 6.1.1 occupying `0x1000..0x26000`. Replacing it needs an SWD debug probe and gains nothing. nrf-sdc does not use the SoftDevice; the slot stays reserved. |
| D7 | Repository is `bark`; crates `bark-proto`, `bark-sim`, `bark-fw`. `bark-fw` is a separate Cargo workspace. | Answers design open item O9. A crate that only builds for `thumbv7em-none-eabihf` cannot share a workspace with host tests without nightly per-package targets. |
| D8 | **`bark-proto` does not allocate.** Tables are fixed-capacity arrays sized by the design. | Every table is bounded by the design anyway (§8.2, §10.2, §10.4). No allocator on the firmware means no allocation failure path; fixed-size `Leaf`s let the simulator hold twenty thousand in cache. |
| D10 | **No failure notices.** The per-hop ACK is the only acknowledgement in the protocol; whether a message arrived is the app's business, inside the encrypted payload. | A network-level notice needs a sender address in the header, which the design keeps out of the header on purpose. Decided 2026-10-14 after the first draft added one. |
| D11 | **DFS state lives in the relay.** Per message it handles, a relay keeps its parent (the short name and home channel of the neighbour the message first came from; none if it originated the message) and the set of neighbours it has tried, the parent included. The owner relay remembers delivered IDs for the queue TTL. | Backtracking needs to know who sent a repeat; DATA names its sender in `src_hop` (D16). Revised 2026-10-14, twice: the first draft keyed on visited-list length alone, which cannot tell a retransmission from a backtrack when the child's append was lost; the second kept a visited list in the packet as skip list and sender identity, which D16 removes. (Spec §9.2.) |
| D12 | **Neighbour-table eviction keeps incumbents.** When the table is full and a new relay is heard, it replaces the least recently heard demoted entry, else the least recently heard entry not heard for a worst-case rotation (13 × 15 s = 195 s), else it is not added. (`tables/neighbours.rs`, spec §8.2.) | Least-recently-heard eviction, the first draft, fails on a rooftop relay hearing ≈270 relays: ≈2 heartbeats a second on its channel would evict a live neighbour every ≈30 s and lose every failure count within a minute. Keeping incumbents holds an equally arbitrary 64 and replaces only entries that fail or fall silent. Whether a set spread around the relay routes better stays open (O4). Decided 2026-10-14. |
| D13 | **Preamble 12 symbols** on every packet except those to sleeping leaves; airtime by the datasheet formula (`radio.rs` `time_on_air`): heartbeat 11.8 ms, ACK 11.8 ms (9 bytes, D19), 255-byte frame 138.6 ms. **The channel sweep is spread:** one RSSI reading every ≈77 ms instead of 13 in a burst each second. | The SX1262 needs at least 12 preamble symbols at SF5 and SF6 (datasheet §6.1.4); the first draft assumed 8. With 12, a single reading (≈0.5 ms away) is shorter than the preamble left after the modem locks, so a spread sweep loses no packets, where a 5 ms burst loses ≈0.4% of arrivals. Holds while the modem locks within 5 symbols; measure in bring-up step 1. Decided 2026-10-14 (closes Q5). (Spec §4, §6.1, §7, §10.5, §13.) |
| D9 | **One timer per core.** The core exposes `next_wakeup()`; the driver delivers `Event::Wakeup` when its clock reaches it. | No timer identifiers cross the boundary; the simulator keeps one heap entry per core, the firmware one embassy timer. Fixed in `docs/core-interface.md`. |
| D14 | **Relays are named on the wire by a 4-byte short name**: the low 16 bits of the latitude count, then the low 16 bits of the longitude count. ATTACH `relay`, DATA `dst_hop` and `src_hop` carry it. Fields used as coordinates, the heartbeat position and DATA `dst_pos`, stay 7 bytes. Identity is still the position (§8.1). | Saves 3 bytes per name. The short name repeats only every 39 km of latitude and 25 km of longitude at 50° N, so among relays one node can hear (≈3 km) it is exactly the position: the receiver rebuilds the full position from its own, and two relays share a name only if they share a 0.6 m cell. A hash would collide with probability ≈10⁻⁵ and could not be inverted. Decided 2026-10-14. (Spec §8.1, §14.) |
| D15 | **No `msg_id` field.** A message is identified by `hash32(dst_pos ‖ dst_leaf ‖ payload)`, computed by every node that handles it; ACK and DELIVER carry it. The app must keep payloads unique (spec §11); encryption with a fresh nonce does. | 4 bytes less per DATA, and nothing for the sender to generate or keep. Two identical messages to one destination within the dedupe window are one message, which the app avoids for free. Decided 2026-10-14. (Spec §11, §14.) |
| D16 | **No visited list in the packet** (revises D11). DATA carries `src_hop`, the sender's short name, and its home channel in `aux`. Next-hop candidates exclude only the relay's tried set. A neighbour that already has the message by another path is found out by sending it there: it sends the message straight back, and the sender counts it as tried. | The list cost 2 bytes per relay on every packet and still needed the receiver to resolve the sender. Without it a neighbour that already has the message costs one extra round trip, which overhearing would save, but neighbours sit on different channels and cannot overhear each other. The walk is still a depth-first traversal with a tried set and parent per relay; the `hops` cap remains the backstop for expired state. Decided 2026-10-14. (Spec §9.2, §14.) |
| D17 | **How a relay runs the search** (spec §9.2). Candidates are tried in order of distance to the destination, so the tried set is the parent plus everything up to the last child. A repeat is a copy when its `hops` is no higher than any received before; a copy, a repeat from the parent or from an earlier child, and any repeat at the owner are only ACKed; a repeat from the last child continues the search; a repeat from anyone else is sent straight back. Records expire after 188 s idle, at most 654, least recently active replaced. The owner is the addressed relay, or a relay within 50 m with no closer neighbour; farther away, no closer neighbour means a gap. Send queue of 10; no ACK when it is full. | The `hops` test catches a retransmitted return from a child, which a sender-only rule would take as a second return and so split the search. ACK-only for the parent and earlier children keeps one copy of the message searching. The ordered tried set needs no list. Record lifetime covers the longest search the hop cap allows; the bound is the most messages the duty cycle lets a relay handle in that time. The 50 m rule separates a dead destination from a gap; the old rule made every gap an owner. Decided 2026-10-14.  Revised 2026-10-14: the tried set is explicit, the parent plus the neighbours actually handed the message (one bit per neighbour slot); a neighbour passed over because it was demoted, expired or not in the table is not tried, so its later offer is sent back (case 6) rather than dropped. The implicit, order-defined set dropped the only searching copy in that case. |
| D18 | **Demotion is not cleared by a heartbeat.** A demoted neighbour returns to use when it ACKs a packet from this relay or after three rotations. | A heartbeat proves the neighbour is alive, not that it hears us. On a link that works one way only, clearing demotion every heartbeat would make every message pay the failed attempts again. (Spec §8.2.) |
| D19 | **ACKs name their sender.** ACK carries the message ID and the acknowledging relay's short name or the leaf's ID; the sender matches both. | Relays share home channels, and the search can put the same message in two relays on one channel; a bare ACK could then end the wrong hand-over and strand the message. Cost 4 bytes, 1.3 ms per hop. (Spec §9.3, §14.) |
| D20 | **`lora-phy` pinned to upstream `main` `7a9c2ec` (2026-10-06), with the firmware's own board interface** (`bark-fw/src/radio.rs`, `Pins`) rather than the driver's generic SX126x one. | That revision reports CRC failures as errors. The generic interface polls BUSY at once after each command, within the up to 600 ns BUSY takes to rise (SX1261/2 DS §8.3.1), and waits on BUSY and DIO1 without bound; ours waits out the rise, bounds both, and so needs no fork. Open, measured in bring-up step 1: the driver starts every operation from STDBY_RC, so each retune, CAD and transmit may wait out its 10 ms TCXO start (DS §13.3.6), against the ≈0.1 ms §6.1 assumes. |

## Phases

### Phase 0: skeleton and protocol core (now)

- Cargo workspace, CI for host tests.
- `bark-proto`: wire codecs for every packet in design §14 (heartbeat, ACK, ATTACH, DATA, DELIVER), the 7-byte position codec (§7), local tangent-plane distance (§11), neighbour table, leaf table, delivery queue, recently received IDs, busy estimator and home-channel rule (§6), heartbeat scheduler (§7), per-hop transfer state machine (§9.3), duty-cycle budget (§3).
- Tables and routing: per-message DFS records (§9.2), a neighbour table keyed by 7-byte position with channel and `fail_count` and expiry after three rotations, and a routing function that picks the neighbour nearest the destination, falls back to DFS when no neighbour is closer, and applies the owner rule (§9.2) for leaves.
- Exit criterion: every codec round-trips under property tests; a two-node unit test exchanges heartbeat, ATTACH, DATA, ACK through the core with a fake clock.

### Phase 1: simulator (until boards arrive, ~2026-11-04)

See `simulator-design.md`. Milestones:

1. Three relays in a line, one leaf: greedy forward, ACK, demotion when the middle relay dies. Mirrors bench step 4 so the same scenario later runs on hardware.
2. One km² block, ~10 relays, ~80 leaves: attach, keepalive, delivery, queue (bench step 5).
3. Channel selection: inject a busy channel, confirm avoidance and no oscillation among relays that all hear each other (bench step 3).
4. Capacity: a 28 km² collision domain, ~270 relays, 20k leaves, texts at the §13 rates. Measure delivery ratio, latency, per-channel busy fraction, per-relay airtime, where the 10% cap binds first.
5. Sweep the unknowns: adjacent-channel rejection at 125 kHz spacing (bench item C1), hearing radius, SF5 sensitivity, heartbeat interval. Produce the table that replaces §13.

### Phase 2: bring-up (boards in hand)

Design §15 steps 1 to 3 on real boards with `lora-phy` git: transmit and receive at SF5, channel activity detection (CAD), signal strength (RSSI) read, retune time, sweep time, noise floor, adjacent-channel rejection with two boards and attenuators. Every measurement goes back into the simulator parameters. Toolchain: `thumbv7em-none-eabihf` target, a UF2 converter, logging (defmt) over USB serial (debug pad location unconfirmed).

### Phase 3: protocol on hardware

Steps 4 and 5 with four boards (three relays in a line plus one leaf), then BLE GATT and a minimal phone app (Flutter; flutter_rust_bridge is already installed here). Field test needs more boards or RAK4631 EU433 relays (research doc, procurement).

## Open questions for discussion

- **Q1 (D3), decided 2026-10-14.** The core does no I/O. An async node task would need a mini-executor in the simulator and makes 20k simulated leaves expensive. The contract is `docs/core-interface.md`.
- **Q2.** Link model fidelity. Start with a user-supplied table of received power for each pair of nodes in range, plus a few generators (log-distance with exponent, rooftop bonus, indoor wall loss). A terrain model (free-space loss plus per-cell attenuation along the path) can be one generator, not the primary interface.
- **Q3.** Leaf behaviour model: static, random walk, or trace-driven? Phones in pockets go dark for minutes; that drives the delivery-queue sizing (§10.4).
- **Q4.** Whether the simulator exercises the real wire format (bytes through the codec) or passes structs. Recommendation: real bytes, so a codec bug is a simulator failure too, and airtime is computed from actual lengths.
- **Q5 (D13), decided 2026-10-14.** The 8-symbol preamble was wrong for SF5 (12 minimum). The spec now uses 12 everywhere, and the sweep-loss argument, redone, spreads the sweep.
- **Q6.** Scenario file format: Rust builder only, or a TOML/RON file so scenarios can be shared and diffed? Recommendation: both, with the file format as the stable interface.

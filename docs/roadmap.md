# Roadmap and decisions

**Status:** 2026-10-15. "The design" and § numbers refer to `protocol.md`.

## Decisions

| # | Decision | Why |
|---|---|---|
| D1 | **The protocol core owns its routing and table code**; `bark-proto` takes no external routing or mesh dependency. | The design's routing is small and specific: forwarding toward a 7-byte position that is also the relay identity, depth-first search (DFS) around gaps with per-message state in each relay, per-hop acknowledgement (ACK) with demotion. A general mesh library brings network-wide tables, position estimation and node IDs the design leaves out (§12), and pins its own embassy versions. A few hundred lines of our own keep the API shaped by the design alone. |
| D2 | **Simulator first.** Before any firmware, build a discrete-event simulator that places relays and leaves on a grid, takes a sparse pairwise signal-power table (only pairs in range, per channel, varying over time), and runs traffic through the real protocol core. | The design's capacity numbers (§13) are order-of-magnitude estimates with 2× uncertainty on hearing radius and hop count. The thresholds in O3 and the eviction policy in O4 can only be tuned against a model. Boards arrive in three weeks; the simulator is useful now and after. |
| D3 | **The protocol core does no I/O** (`bark-proto`): a state machine driven by `(event, now)` that returns actions; no executor, no async, no radio driver. Firmware wraps it in an embassy task; the simulator drives it from an event queue. | One implementation under test in both places. Thousands of nodes in one process need a core that does not own tasks or channels. Decided 2026-10-14 (Q1). |
| D4 | `lora-phy` from the lora-rs **git main**, not crates.io 3.0.1 (July 2024). | SF5, `get_rssi`, arbitrary sync word, `rx_switch_channel`, duty-cycled receive all landed after 3.0.1. Pin a revision. |
| D5 | BLE via **TrouBLE + nrf-sdc**, not nrf-softdevice. | nrf-softdevice last released January 2024; trouble-host 0.8 and nrf-sdc 0.4 both released August 2026 with GATT, notifications and security. Known to run on a T-Echo. |
| D6 | **Keep the stock bootloader.** Application linked at `0x26000`, flashed as UF2 (family `0xADA52840`, volume `TECHOBOOT`). | The T-Echo ships Adafruit's UF2 bootloader with SoftDevice S140 6.1.1 occupying `0x1000..0x26000`. Replacing it needs an SWD debug probe and gains nothing. nrf-sdc does not use the SoftDevice; the slot stays reserved. |
| D7 | Repository is `bark`; crates `bark-proto`, `bark-sim`, `bark-fw`. `bark-fw` is a separate Cargo workspace. | Answers design open item O9. A crate that only builds for `thumbv7em-none-eabihf` cannot share a workspace with host tests without nightly per-package targets. |
| D8 | **`bark-proto` does not allocate.** Tables are fixed-capacity arrays sized by the design. | Every table is bounded by the design anyway (§8.2, §10.2, §10.4). No allocator on the firmware means no allocation failure path; fixed-size `Leaf`s let the simulator hold twenty thousand in cache. |
| D10 | **No failure notices.** The per-hop ACK is the only acknowledgement in the protocol; whether a message arrived is the app's business, inside the encrypted payload. | A network-level notice needs a sender address in the header, which the design keeps out of the header on purpose. Decided 2026-10-14 after the first draft added one. |
| D11 | **DFS state lives in the relay.** Per message it handles, a relay keeps its parent (the short name and home channel of the neighbour the message first came from; none if it originated the message) and the set of neighbours it has tried, the parent included. The owner relay remembers delivered IDs for the queue TTL. | Backtracking needs to know who sent a repeat; DATA names its sender in `src_hop` (D16). Revised 2026-10-14, twice: the first draft keyed on visited-list length alone, which cannot tell a retransmission from a backtrack when the child's append was lost; the second kept a visited list in the packet as skip list and sender identity, which D16 removes. (Spec §9.2.) |
| D12 | **Neighbour-table eviction keeps incumbents.** When the table is full and a new relay is heard, it replaces the least recently heard demoted entry, else the least recently heard entry not heard for a worst-case rotation (13 × 15 s = 195 s), else it is not added. (`tables/neighbours.rs`, spec §8.2.) | Least-recently-heard eviction, the first draft, fails on a rooftop relay hearing ≈270 relays: ≈2 heartbeats a second on its channel would evict a live neighbour every ≈30 s and lose every failure count within a minute. Keeping incumbents holds an equally arbitrary 64 and replaces only entries that fail or fall silent. Whether a set spread around the relay routes better stays open (O4). Decided 2026-10-14. |
| D13 | **Preamble 12 symbols** on every packet except those to sleeping leaves; airtime by the datasheet formula (`radio.rs` `time_on_air`): heartbeat 11.8 ms, ACK 11.8 ms (9 bytes, D19), 255-byte frame 138.6 ms. **The channel sweep is spread:** one RSSI reading every ≈77 ms instead of 13 in a burst each second. | The SX1262 needs at least 12 preamble symbols at SF5 and SF6 (datasheet §6.1.4); the first draft assumed 8. With 12, a single reading (≈0.5 ms away) is shorter than the preamble left after the modem locks, so a spread sweep loses no packets, where a 5 ms burst loses ≈0.4% of arrivals. Holds while the modem locks within 5 symbols; measure in bring-up step 1. Decided 2026-10-14 (closes Q5). (Spec §4, §6.1, §7, §10.5, §13.) |
| D9 | **One timer per core.** The core exposes `next_wakeup()`; the driver delivers `Event::Wakeup` when its clock reaches it. | No timer identifiers cross the boundary; the simulator keeps one heap entry per core, the firmware one embassy timer. Fixed in `docs/core-interface.md`. |
| D14 | **Relays are named on the wire by a 4-byte short name**: the low 16 bits of the latitude count, then the low 16 bits of the longitude count. ATTACH `relay`, DATA `dst_hop` and `src_hop` carry it. Fields used as coordinates, the heartbeat position and DATA `dst_pos`, stay 7 bytes. Identity is still the position (§8.1). | Saves 3 bytes per name. The short name repeats only every 39 km of latitude and 25 km of longitude at 50° N, so among relays one node can hear (≈3 km) it is exactly the position: the receiver rebuilds the full position from its own, and two relays share a name only if they share a 0.6 m cell. A hash would collide with probability ≈10⁻⁵ and could not be inverted. Decided 2026-10-14. (Spec §8.1, §14.) |
| D15 | **No `msg_id` field.** A message is identified by `hash32(dst_pos ‖ dst_leaf ‖ payload)`, computed by every node that handles it; ACK and DELIVER carry it. The app must keep payloads unique (spec §11); encryption with a fresh nonce does. | 4 bytes less per DATA, and nothing for the sender to generate or keep. Two identical messages to one destination within the dedupe window are one message, which the app avoids for free. Decided 2026-10-14. (Spec §11, §14.) |
| D16 | **No visited list in the packet** (revises D11). DATA carries `src_hop`, the sender's short name, and its home channel in `aux`. Next-hop candidates exclude only the relay's tried set. A neighbour that already has the message by another path is found out by sending it there: it sends the message straight back, and the sender counts it as tried. | The list cost 2 bytes per relay on every packet and still needed the receiver to resolve the sender. Without it a neighbour that already has the message costs one extra round trip, which overhearing would save, but neighbours sit on different channels and cannot overhear each other. The walk is still a depth-first traversal with a tried set and parent per relay; the `hops` cap remains the backstop for expired state. Decided 2026-10-14. (Spec §9.2, §14.) |
| D17 | **How a relay runs the search** (spec §9.2). Candidates are tried in order of distance to the destination, so the tried set is the parent plus everything up to the last child. A repeat is a copy when its `hops` is no higher than any received before; a copy, a repeat from the parent, and any repeat at the owner are only ACKed; a repeat from the last child continues the search; a repeat from anyone else, an earlier child included, is sent straight back. Records expire after 188 s idle, at most 626, least recently active replaced. The owner is the addressed relay, or a relay within 50 m with no closer neighbour; farther away, no closer neighbour means a gap. Send queue of 10; no ACK when it is full. | The `hops` test catches a retransmitted return from a child, which a sender-only rule would take as a second return and so split the search. ACK-only for the parent keeps one copy of the message searching. The ordered tried set needs no list. Record lifetime covers the longest search the hop cap allows; the bound is the most messages the duty cycle lets a relay handle in that time. The 50 m rule separates a dead destination from a gap; the old rule made every gap an owner. Decided 2026-10-14.  Revised 2026-10-14: the tried set is explicit, the parent plus the neighbours actually handed the message (one bit per neighbour slot); a neighbour passed over because it was demoted, expired or not in the table is not tried, so its later offer is sent back (case 6) rather than dropped. The implicit, order-defined set dropped the only searching copy in that case. Revised 2026-10-15: an earlier child's repeat is sent straight back, no longer only ACKed. The child may be offering its own searching copy, which ACK-only ended without a trace: it had the message already and sent this relay's hand-over straight back, or it never took a hand-over this relay counted as failed because its replies were lost, and got the message later by another path. Seen in 25-relay random meshes (`tests/routing.rs`: `an_earlier_child_that_had_the_message_is_sent_it_back`, `an_earlier_child_whose_hand_over_failed_is_sent_it_back`; both fail under ACK-only). Where the child is returning a copy it did take, after a split, it only ACKs the send-back, since this relay is its parent, and one copy goes on (`a_split_copy_returned_by_an_earlier_child_ends_there`). The record bound is 626 (⌊18.83 s / 30.08 ms⌋); this row said 654. Simulator, settled phase: S1, seeds 1–40, 1.000, and S1b, seeds 1–100, 0.961, worst 0.900, bit-identical; S2, seeds 1–100, 0.878, worst 0.619, the same delivery and losses in every seed, with frames differing in 3 seeds where the case arose. |
| D18 | **Demotion is not cleared by a heartbeat.** A demoted neighbour returns to use when it ACKs a packet from this relay or after three rotations. | A heartbeat proves the neighbour is alive, not that it hears us. On a link that works one way only, clearing demotion every heartbeat would make every message pay the failed attempts again. (Spec §8.2.) |
| D19 | **ACKs name their sender.** ACK carries the message ID and the acknowledging relay's short name or the leaf's ID; the sender matches both. | Relays share home channels, and the search can put the same message in two relays on one channel; a bare ACK could then end the wrong hand-over and strand the message. Cost 4 bytes, 1.3 ms per hop. (Spec §9.3, §14.) |
| D20 | **`lora-phy` pinned to upstream `main` `7a9c2ec` (2026-10-06), with the firmware's own board interface** (`bark-fw/src/radio.rs`, `Pins`) rather than the driver's generic SX126x one. | That revision reports CRC failures as errors. The generic interface polls BUSY at once after each command, within the up to 600 ns BUSY takes to rise (SX1261/2 DS §8.3.1), and waits on BUSY and DIO1 without bound; ours waits out the rise, bounds both, and so needs no fork. Open, measured in bring-up step 1: the driver starts every operation from STDBY_RC, so each retune, CAD and transmit may wait out its 10 ms TCXO start (DS §13.3.6), against the ≈0.1 ms §6.1 assumes. |
| D21 | **The destination position alone decides who delivers.** A relay delivers or queues a message for a leaf only if it owns the destination position (§9.2.7), never because the leaf is in its leaf table. | Simulator S1, 40 seeds: 4 seeds lost 1 to 3 messages each in the settled phase (8 in all, `QueueExpired` at B). Both leaves first attached to the middle relay B, heard at −110 dBm, and moved to their own relays one or two rotations later (§10.1). B kept the far leaf in its leaf table for up to 180 s after it left (§10.2), took messages addressed to the far leaf at C from the near leaf, still attached to B, as its own to deliver, queued them on its own channel where nobody answered, and dropped them after the 10-minute delivery TTL. With the rule: 40 of 40 seeds deliver every settled-phase message. The table can also be right where the address is stale, for a leaf that has moved to this relay: delivering from the table would save such a message when this relay happens to be its origin or on its path. The rule gives that up; it is the loss the design already accepts for a moved leaf (§10.4), and one rule, by the address, replaces two that disagree exactly when a leaf moves. Decided 2026-10-14. (Spec §9.2.7.) |
| D22 | **The retry wait after a missing ACK is derived from the hand-over time.** Retry k after k unanswered transmissions waits uniform in [0, 2^k × 150.4 ms], 150.4 ms being a full frame and its ACK (`tables::RETRY_BACKOFF`); 0–301 ms, then 0–602 ms. The listen-before-talk backoff stays 0–50 ms. The send queue, sized by the time an upstream sender spends retrying, grows from 10 to 16 (revises D17), and the `Relay` from 48 304 to 49 880 B. Closes O14. | Two senders that cannot hear each other and collide at one receiver both miss the ACK; their retries miss each other only if they start more than one hand-over apart, with probability (1 − 1/W)² for a window of W hand-overs: zero for the old 50 ms. Simulator S1b (`scenarios/s1b-hidden.toml`: S1's line, a leaf at each end, both sending every 30 s from the same instant, so every first hand-over to the middle relay collides), 20 seeds, settled-phase delivery: old rule 0.136 mean (5 seeds delivered nothing; every loss a `NoRoute` drop at A or C after the hand-over to B failed, most of them while B was demoted); fixed window of one hand-over 0.553; growing 1, 2 hand-overs 0.694; 2, 3 hand-overs 0.905; **2, 4 hand-overs 0.958** (7 of 20 seeds 1.0, worst 0.688). Median per-seed p50 latency 599 ms against 205 ms in S1, the price of a retry on every message; S1 is unchanged (40 of 40 seeds 1.0). Most of what is still lost comes from demotion: two failed hand-overs demote B, the only route, and every message is then dropped until the demotion lapses (S1b with demotion off: 0.971). Decided 2026-10-14. (Spec §9.3, §16.) |
| D23 | **A leaf keeps its relay through a fade** (spec §10.1, §10.2). It chooses the strongest relay by the mean RSSI of its last two heartbeats after listening a worst-case rotation (195 s) from the first heartbeat it hears, or at once if it has a message to send; it switches only to a relay heard over two heartbeats and 8 dB stronger; it gives its relay up only after failed hand-overs in two keepalive periods in a row, or 390 s without hearing it; and it holds a message it cannot hand over for up to the 10-minute delivery TTL instead of failing it at once. The leaf tracks four relays besides its own; `Leaf` grows from 704 to 832 B. | The leaf attached to the first relay it heard, and one failed keepalive, three attempts inside one fade, cost it its relay; texts sent meanwhile failed at once with `NoRelay`. The 8 dB is two standard deviations of the difference of two two-heartbeat means under the scenarios' 4 dB fading (heartbeats of one relay reach a leaf ≈130 s apart, past the 60 s fading correlation time). Simulator S2 (`scenarios/s2-block.toml`), settled-phase delivery, seeds 1–10: 0.793 mean (pooled 221/274) before, **0.861 (230/264)** after, worst seed 0.621 → 0.700; leaf relay changes 174 → 70 an hour over 80 leaves; losses `NoRelay` 29 → 4, `QueueExpired` 13 → 21, `NoAck` 4 → 0, unaccounted 7 → 8. Seeds 1–100: 0.800 → 0.878, relay changes 179 → 73 an hour. Held messages lengthen the tail: per-seed median p90 latency 56 s → 176 s (p50 unchanged, 241 ms). The margin matters little: 6, 8 and 12 dB give 0.880, 0.878 and 0.875 with 84, 73 and 65 relay changes an hour (100 seeds). Most relay changes left follow two failed periods on indoor links within a few dB of sensitivity, after which the leaf takes the next strongest relay and stays there; most messages lost are queued at a relay the leaf has left (`QueueExpired`). S1 is unchanged (40 of 40 seeds 1.0); S1b moves from 0.958 to 0.923 over seeds 1–20, but 0.947 against 0.945 over seeds 1–100, within the spread between seeds. Decided 2026-10-14. |
| D24 | **The home channel's busy estimate counts only foreign traffic** (spec §6.1). Packets addressed to the relay, the ACKs of its own hand-overs, and a home reading taken while one of them was on the air are left out; receptions addressed to others, heartbeats included, and readings above the threshold at other times count. A home reading is held one sweep interval (1 s) until the packet it may have fallen in has ended. | A relay's own traffic follows it to any channel; counting it made a busy relay leave a channel for its own load, which then came along, and messages handed over before its neighbours heard the new channel failed. The three-hour duty-budget scenario (`tests/routing.rs`, F forwarding at its 10 % cap, run with the channels free instead of fixed, 4 h): F's home moves 1.25 → 0 an hour, D's 1.25 → 0.75, O's 0 → 0. D's remaining moves come from the frames that test discards on the way to D: on the air at D but never received, they cannot be told from other nodes' traffic, as a real packet that fails its CRC cannot. A relay sent a full frame every 2 s (7 % of its channel) moved and lost a message before; now it stays, its home estimate at 0.09 % (`a_relay_does_not_flee_its_own_traffic`). S1, S1b and S2 are unchanged: no relay moves after its boot choice in them, before or after, since no channel is more than ≈0.3 % busy. Decided 2026-10-14. |
| D25 | **A demoted neighbour is the last resort** (spec §8.2, §9.2.3). When no live undemoted neighbour is left to try, the next-hop function takes demoted ones, in the same order, before returning to the parent or dropping; their failures count as usual. | Demotion is meant to stop a failing link from costing every message its attempts while another route exists, not to drop messages whose only route it is. In S1b two hand-overs lost to hidden-terminal collisions demote B, the only route between A and C, and both then dropped every message for 390 s. Simulator S1b, settled-phase delivery, seeds 1–20: 0.923 mean, worst seed 0.652, before; **0.957, worst 0.913**, after; seeds 1–100: 0.945 → 0.961, worst 0.633 → 0.900. Only the seeds that lost a demotion's worth of messages change; what is left is messages whose three attempts all collided. S1 and S2 settled phases are unchanged. The cost: a neighbour that is really gone is tried, three attempts, by every message that has no other way, until its entry expires 390 s after its last heartbeat; in S1 after B is removed, A drops each message after ≈1 s of attempts instead of at once for the first eleven messages (`line_of_three_loses_its_middle`). Decided 2026-10-14. |
| D26 | **The duty-cycle budget is a token bucket** (spec §3, §9.4; `tables/budget.rs`), replacing the rolling one-hour window. Depth 6 s, one minute at 10 %; rate (360 s − 6 s) per hour, 9.83 %; a transmission starts only if the bucket holds its airtime. Any interval of length L then carries at most 6 s + 9.83 % × L, so any hour at most 360 s, the 10 % of ERC/REC 70-03 band g1 (proof in the module documentation); a rate of a full 10 % with a 6 s depth would allow 366 s in an hour. The heartbeat reserve becomes one heartbeat, 11.84 ms, which the bucket refills in 120 ms. A relay refuses a packet to send on (no ACK, §9.2.4) when its send queue with that packet could not go out within the 2.38 s its sender spends retrying. `Budget` is 16 B for both roles: the `Relay` drops from 49 880 to 49 416 B, the `Leaf` from 832 to 736 B. | The window let a relay at the cap spend its 360 s in a burst and then fall silent for most of an hour. The setup of the three-hour duty-budget test (`tests/routing.rs`: O offers F 2.5 times what F's budget carries), F's airtime per minute: before, 34 minutes at ≈10.4 s (17 %) then 33 minutes at 0.1 s (heartbeats only), over and over, 75 of the 180 minutes with traffic below 0.5 s; longest wait for the budget 1019 s, longest gap between F's DATA frames 1619 s. After: 10.5 s in the first minute, then 5.9 s in every minute; longest wait 1.4 s, longest gap 1.9 s. F forwards 2307 messages instead of 2437 (−5.3 %): the lower rate costs 1.7 %, the rest is hand-overs to D repeated because D's ACKs were lost under O's retries of the messages F refused, which a relay at the edge of its bucket provokes all the time; 32 messages went back to O after four unanswered attempts (§9.2.5). With the old refusal rule (refuse unless the budget allows the packet at once) F also dropped 24 such returns, which O, out of budget itself, refused; the queue rule removes them. S1, S1b and S2 are unchanged: no relay there spends more than 0.5 % of its time on air. Decided 2026-10-14. |
| D27 | **A relay refuses with BUSY** (spec §9.2.4, §9.3, §9.4, §14; replaces the refusal rule of D26 and the silent refusal of D17). BUSY, type 0x7, is the first byte and the refusing relay's short name: 5 bytes, 10.56 ms, sent where the ACK would have gone, with the same listen-before-talk. A relay refuses a packet that would give it work, to send on or to deliver, when its send queue is full or when its bucket holds less than the **reply reserve** and an ACK. The reserve is 22 BUSY replies, those the bucket refills in the 2.38 s a sender spends retrying an unanswered hand-over (9.83 % × 2.38 s = 234 ms, ⌊234 / 10.56⌋ = 22), and a heartbeat: 244.2 ms. Forwarding and the ACKs that take on work leave the reply reserve in the bucket; replies leave the heartbeat reserve; heartbeats leave nothing. A packet that gives no work (§9.2.4 cases 2, 3, 5) is still ACKed: BUSY would send its sender on with a second copy. The sender matches BUSY against its hand-over's receiver and treats it as a listen-before-talk give-up: the neighbour is set aside for this hand-over, not counted as tried, and no failure is counted. It also marks the neighbour busy for 2.48 s, the reserve's refill time; until then other messages take it only after every other candidate, demoted ones included. A refused return to the parent or send-back uses one attempt and is dropped after the last, as an unanswered one was, but no longer counts a failure against the receiver. A leaf told BUSY keeps its relay and the message and offers it again after the hold. `Neighbour` grows from 40 to 48 B: `Relay` 49 416 → 49 928 B, `Leaf` 736 → 744 B. | Silence made a refusing relay look like a failing one: its senders spent their 2.38 s of retries on its channel, as full frames that collide with its own traffic, and counted failures toward demoting a link that works. The three-hour duty-budget test (`tests/routing.rs`: O offers F 2.5 times what F's bucket carries; same seeds), before → after: F forwards 2333 → 2372 (+1.7 %), returns 32 → 1 to O; D receives 2363 → 2373; O's frames to F 7584 → 4746, of them retransmissions 3993 → 426; D's ACKs lost at F under O's frames 307 → 176; longest gap between F's DATA frames 1.91 s both. All 1947 of F's refusals are for a full queue, none below the reserve: forwarding never takes the bucket below it, so only replies can. The price is latency: with refusal only when full, F's queue stays full and drains at the bucket's rate, and O→D latency goes from a median of 13.5 s (max 21.0 s) to 72.1 s (max 78.9 s), each message here costing F three frames. Refusing also when the queue cannot go out within the hold gives 2333 forwarded and a median of 7.8 s (max 10.1 s); left open as O15. Simulator S1b and S2, seeds 1–100, are unchanged (S1b 0.961, worst 0.900; S2 0.878, worst 0.619): no relay in them comes near its cap, and none sends a BUSY. A test floods F with refusals for 65 minutes: its replies run the bucket down to the heartbeat reserve, it stays at 354 s an hour, and no heartbeat waits (`replies_stay_within_the_reserve`). BUSY as decided here named no message, so two senders on one channel handing to the same relay within one reply time, ≈100 ms, could both take a BUSY meant for one of them; D30 adds 16 bits of the message ID. Decided 2026-10-14. |
| D28 | **Scenarios that stress the search, and accounting that names every loss** (`scenarios/`, `simulator-design.md` §6). Three scenarios join S1, S1b and S2: `corridor.toml`, five relays in a line with a leaf at each end, both sending every 30 s from the same instant, so two flows meet head on at every relay; `mesh-burst.toml`, 25 relays at random in a 2.5 km square with S2's link model and a leaf at each, every leaf sending across the mesh at the same instant every 10 minutes; `mesh-spread.toml`, the same with each leaf starting at its own time and the middle relay restarting halfway. A scripted `restart` powers a node off and on: it keeps its position or leaf ID and loses everything else, as a solar relay does after a night. The summary sorts every message into delivered, lost (where and why), in flight (a core still holds it at the end) and unaccounted, and marks a message unreachable when no chain of relays hearing each other above sensitivity joins its origin's relay to its destination's at the start; the delivery ratio is also given over the reachable ones. The scenario tests fail if any message to a reachable destination is unaccounted. | One line, one flow and Poisson traffic never made many relays meet crossing traffic at once, and the bug and the gridlock this set found (D17's revision of 2026-10-15; an unmerged one-place send queue that delivered 44 % of the corridor) went unseen. Counting a message to an isolated relay as the protocol's loss, and a message still queued at the end as lost without a trace, hid what the count is for: S2's 103 unaccounted messages over seeds 1–100 were all in flight. A message to an unreachable destination can still end untraced when it has split in two (§9.5): both copies search the same relays, and a relay whose search for one has ended absorbs the other; one such message in mesh-burst, seed 5. Settled phase at this commit (D1–D27 and D17's revision), seeds 1–10: corridor 0.969 mean, worst 0.934 (seeds 1–3: 0.946, 0.934, 0.978), all 29 losses `NoRoute` at the end relays after three unanswered attempts, median latency 0.72 s; mesh-burst 0.984, worst 0.840, every reachable message delivered (984 of 984), 16 unreachable on seed 5, median latency 1.7 s; mesh-spread 0.973, worst 0.833, reachable 876 of 886, 14 unreachable on seed 5, median latency 0.25 s. S1, S1b and S2 are unchanged. Decided 2026-10-15. |
| D29 | **Overload becomes pushback, not latency and not silent loss.** The rules, decided together; rules (1) and (2) are built, the others not yet. Each becomes its own commit, measured on S1, S1b, S2, the overload test, the corridor and the meshes, in this order. (1) *Admission by rate, not by occupancy.* A relay takes a packet that gives it work only if the airtime of everything it holds, that packet included, fits in its duty bucket as it stands (D26, with D27's reserves left in); otherwise it answers BUSY. The send queue's places follow from the bucket's depth over a full frame and its ACK, about 40; the memory comes from the delivery store, sized by how long leaves sleep. The store feeds the queue whenever there is room, and a message for an own leaf is refused when the store is full, not displaced. Closes O15. *Built 2026-10-15* (spec §9.2.4, §9.3, §9.4, §10.4, §16; `core-interface.md` §6): a relay takes a packet to send on only if its send queue has a place and its bucket holds the ACK, the airtime of every queued frame and of the new one, and the reply reserve; its own application's message likewise, without the ACK. The queue has ⌈6 s / 150.4 ms⌉ = 40 places: for full frames the bucket binds first (a full bucket takes at most 38 with the reply reserve left), for short frames the places, which forty short hand-overs empty in a few seconds. ## Phases

### Phase 0: skeleton and protocol core (now)

- Cargo workspace, CI for host tests.
- `bark-proto`: wire codecs for every packet in design §14 (heartbeat, ACK, ATTACH, DATA, DELIVER, BUSY), the 7-byte position codec (§7), local tangent-plane distance (§11), neighbour table, leaf table, delivery queue, recently received IDs, busy estimator and home-channel rule (§6), heartbeat scheduler (§7), per-hop transfer state machine (§9.3), duty-cycle budget (§3).
- Tables and routing: per-message DFS records (§9.2), a neighbour table keyed by 7-byte position with channel and `fail_count` and expiry after three rotations, and a routing function that picks the neighbour nearest the destination, falls back to DFS when no neighbour is closer, and applies the owner rule (§9.2) for leaves.
- Exit criterion: every codec round-trips under property tests; a two-node unit test exchanges heartbeat, ATTACH, DATA, ACK through the core with a fake clock.

### Phase 1: simulator (until boards arrive, ~2026-11-04)

See `simulator-design.md`. Milestones:

1. Three relays in a line, one leaf: greedy forward, ACK, demotion when the middle relay dies. Mirrors bench step 4 so the same scenario later runs on hardware.
2. One km² block, ~10 relays, ~80 leaves: attach, keepalive, delivery, queue (bench step 5).
3. Channel selection: inject a busy channel, confirm avoidance and no oscillation among relays that all hear each other (bench step 3).
4. Capacity: a 28 km² collision domain, ~270 relays, 20k leaves, texts at the §13 rates. Measure delivery ratio, latency, per-channel busy fraction, per-relay airtime, where the 10% cap binds first.
5. Sweep the unknowns: adjacent-channel rejection at 125 kHz spacing (bench item C1), hearing radius, SF5 sensitivity, heartbeat interval. Produce the table that replaces §13.

### Phase 2: bring-up (boards in hand)

Design §15 steps 1 to 3 on real boards with `lora-phy` git: transmit and receive at SF5, channel activity detection (CAD), signal strength (RSSI) read, retune time, sweep time, noise floor, adjacent-channel rejection with two boards and attenuators. Every measurement goes back into the simulator parameters. Toolchain: `thumbv7em-none-eabihf` target, a UF2 converter, logging (defmt) over USB serial (debug pad location unconfirmed).

### Phase 3: protocol on hardware

Steps 4 and 5 with four boards (three relays in a line plus one leaf), then BLE GATT and a minimal phone app (Flutter; flutter_rust_bridge is already installed here). Field test needs more boards or RAK4631 EU433 relays (research doc, procurement).

## Open questions for discussion

- **Q1 (D3), decided 2026-10-14.** The core does no I/O. An async node task would need a mini-executor in the simulator and makes 20k simulated leaves expensive. The contract is `docs/core-interface.md`.
- **Q2.** Link model fidelity. Start with a user-supplied table of received power for each pair of nodes in range, plus a few generators (log-distance with exponent, rooftop bonus, indoor wall loss). A terrain model (free-space loss plus per-cell attenuation along the path) can be one generator, not the primary interface.
- **Q3.** Leaf behaviour model: static, random walk, or trace-driven? Phones in pockets go dark for minutes; that drives the delivery-queue sizing (§10.4).
- **Q4.** Whether the simulator exercises the real wire format (bytes through the codec) or passes structs. Recommendation: real bytes, so a codec bug is a simulator failure too, and airtime is computed from actual lengths.
- **Q5 (D13), decided 2026-10-14.** The 8-symbol preamble was wrong for SF5 (12 minimum). The spec now uses 12 everywhere, and the sweep-loss argument, redone, spreads the sweep.
- **Q6.** Scenario file format: Rust builder only, or a TOML/RON file so scenarios can be shared and diffed? Recommendation: both, with the file format as the stable interface.

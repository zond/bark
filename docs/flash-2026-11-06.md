# Room in the image slot (2026-11-06)

**Status:** measured on the node image of `df91ecf`; three changes made
(What was done), the rest recommended or rejected with their numbers.

## The question

The running slot is 98 pages, 401 408 B (`bark-image/src/layout.rs`).
The node image was 377 936 B, 23 472 B free, and had grown 26 KB since
2026-11-05. Pairing may need tens of KB more. Where do the bytes go, and
how much room can be made?

## How it was measured

Every number is the flash image `scripts/uf2.py` writes: the vector
table, `.text`, `.rodata` and the initial values of `.data`. Each
option was built (`cargo build --release` from `bark-fw/`, stable Rust
1.98.0, or nightly 2026-09-25 where marked) and the image's size read
back; the accounting uses `cargo bloat` and `llvm-nm --size-sort` on
the same ELF. Debug info is not in the image. A saving of a few tens of
bytes is noise: any change moves code and constants around.

## Where the bytes go

The image of `df91ecf`: `.text` 329 988 B, `.rodata` 38 288 B, `.data`
9 400 B. By crate, `.text` only, after the changes below (`opt-level =
"z"`), 284.6 KiB in all:

| Crate | KiB | What |
|---|---|---|
| bark-proto | 54.2 | the core; `Node::handle` alone 19.7 |
| embassy-executor | 39.9 | our tasks' bodies, inlined into each task's poll: main task 8.1, radio 7.1, phone 5.6, GPS 5.4, screen 4.9, USB 4.1 |
| bark-driver | 28.8 | the driver 13.5, the SX1262's start-up 4.9 |
| std | 27.2 | `core::fmt`, panics, integer division, soft `f64`, `memcpy` |
| unnamed | 25.7 | the controller's and the MPSL's internal functions |
| trouble-host | 21.3 | the BLE host |
| nrf-sdc-sys | 20.5 | the BLE controller library |
| bark-fw | 18.9 | the GATT service's serving loop 9.9 |
| embassy-futures | 12.7 | the BLE host's three runners, inlined into the `select3` that joins them |
| nrf-mpsl-sys | 10.7 | the MPSL library |
| others | 25 | embassy-nrf 3.4, libm 3.1, embassy-usb 2.9, bark-app-layer 2.8, nrf-mpsl 2.2, bt-hci 1.7, lora-phy 1.5, the sealing crypto 1.6, bark-screen 1.0 |

The phone link, host, controller, MPSL and service together, is about
85 KiB; the radio's core and driver about 90 KiB.

Across crates, in the `"s"` image of `df91ecf`:

- **Formatting.** 120 `Debug` and `Display` implementations take
  20.4 KB of code, 16.6 KB of it `Debug`. The largest are the event
  trace's `Debug` (2.2 KB, the driver's trace line), the BLE host's
  error (1.7 KB), the controller's status codes (1.2 KB, with 1.9 KB of
  their names in `.rodata`) and the ATT requests (0.8 KB). Every log
  line together costs 32.6 KB (27.3 KB at `"z"`): the image built with
  `log`'s `max_level_off`.
- **Panics.** About 500 call sites: 241 "async fn resumed after
  completion", 89 formatted, 100 bounds and slice checks. Each carries
  a source location; together with their file names these are about
  28 KB (`-Zlocation-detail=none`, below).
- **`.data`**: 9.4 KB of initial values, nearly all three statics: the
  BLE host's packet pool (4 036 B), the mailbox's `HOME` (2 288 B) and
  the USB logger (2 092 B). Each is in `.data` because some byte of its
  initial value is not zero.
- **Floating point**: 8.6 KB of `libm` and the compiler's builtins,
  the soft `f64` of `LocalPlane::new` and `powf`, `sin` and `cos`. No
  float is formatted or parsed.
- **Duplicates**: `Node<256, 41>` is the only instance of the core; no
  function is instantiated twice at different sizes for more than a few
  hundred bytes.
- **The console** leaves nothing in the node image (no `console`
  symbol). The font is 5 × 7 bitmaps; `bark-screen` is 1.0 KiB in all.
  `panic-persist` is 522 B.
- **Feature trims** save nothing: what a feature adds and the image
  does not call is removed by LTO. `crypto_box` and `curve25519-dalek`
  are in the dependency tree and contribute 18 B; `usbd-hid`, pulled
  in by `embassy-usb`'s default features, contributes none.

## The options, measured

Change in the image, in bytes; negative is smaller. "s" rows are
against `df91ecf` (377 936 B), "z" rows against the image with the
changes made (340 992 B).

**Compiler and linker**

| Option | Δ | Note |
|---|---|---|

| `"z"`, but `"s"` for bark-proto and bark-driver | s: −26 240 | keeps the core's speed, 3.9 KB less room |
| `"z"` for the BLE crates only, by per-package overrides | s: +2 672 | larger: with fat LTO the root crate's level drives the optimisation after LTO |

The nightly options would tie the firmware to a dated nightly whose
flags may change, and each removes what a panic or a log line tells
from a board nobody watches. They are not recommended; they are the
reserve if nothing else is left.

**Logging**, against the image with the changes made unless marked:

| Option | Δ |
|---|---|
| no log lines at all (`max_level_off`) | −27 296 |
| warnings and errors only (`max_level_warn`) | −14 560 |
| the driver's trace line, `{:?}` of every trace event | −3 104 |
| s: the 10 s driver line | −928 |
| s: `node.rs`'s 17 lines | −6 488 |
| s: `ble.rs`'s 17 lines, most of the host's `Debug` with them | −9 400 |
| s: `update.rs`'s 11 lines | −1 408 |
| s: `node.rs`'s 17 lines as `defmt` | −1 088 |

`defmt` was tried on `node.rs` with a logger that writes its frames to
a buffer: the format strings leave flash, but each argument becomes a
call, and every argument that is a type of ours (the position, the
boot facts, the stored state) still goes through `core::fmt` unless it
gets a `defmt` implementation. It saves a sixth of what the lines cost,
and reading the log would need the ELF and a decoder on the host. Not
worth converting.

**Code**, against the image named:

| Change | Δ |
|---|---|
| `expect` on the GATT server's `Result<_, &str>`, displayed instead | z: −6 704; done |
| the standard library's source path remapped | z: −144; done |
| `HOME` and the USB logger built at boot into a `StaticCell` instead of in `.data` | z: −4 192, the same bytes moved to `.bss` |
| `join(host, link)` in `ble.rs` as two tasks | s: −696, RAM +104 B |
| the BLE host's runner split into its three runners, each a task | s: +312, RAM +160 B |
| `join3` in the main task | 0: it is in the console build only |

The `expect`: `Debug` on a `&str` escapes it, which links the Unicode
property tables and the character escaping; nothing else in the image
formats a `&str` with `Debug`.

The joins. The BLE host's runner joins its receive, control and send
loops in a `select3` (12.7 KiB above); the pairing feature adds about
5.6 KB there. Our code can reach them, `Runner::split` is public, but
the bytes are the three loops' bodies, not the join: as three tasks
they cost 312 B more. Only the host crate, by its features or a change
to it, removes them. Splitting our own `join(host, link)` saves 696 B
and needs the stack, the server and the device name in statics: real
but small, in the file pairing is changing now; not taken.

**Layout**, from `bark-image/src/layout.rs`:

- The slots must stay paired: embassy-boot's swap needs the staged slot
  at least a page larger than the running one (`BootLoader::new`), so
  every page freed elsewhere gives each image half a page.
- The 22 pages of coded pieces, unused until the update over the mesh
  exists, would make the slots 109 and 110 pages: **+45 056 B** for the
  image. The record moves to `0xE1000`, still below `0xEA000`, where
  the bootloader's drive stops writing (`docs/softdevice-2026-11-05.md`);
  the mailbox and the stored state stay where they are; the loader's
  state page needs 2 + 4 × 109 = 438 of its 1024 words; a swap takes
  28 s instead of 25 s. The cost today is a rebuilt loader and one UF2
  with `--loader` per bench board. It cannot be taken back once boards
  are in the field, and the first field image must already hold the
  update's receiving side (`docs/mesh-update-2026-10-25.md`, "What must
  be fixed before the first field deployment"), which needs those
  pages. Lending them only postpones the question to the field freeze.
- The mailbox's ring of 16 pages holds 256 items, eleven days at 23 a
  day. Halved, 128 items and 5.6 days, it gives **+16 384 B** for the
  image. Whether five days is enough is a question about people, not
  flash.
- The loader's spare fourth page alone gives nothing: one page cannot
  be split between the two slots.

## What was done

On branch `worktree-agent-flash`, each its own commit:

| Commit | Image | Δ |
|---|---|---|
| `df91ecf`, before | 377 936 B | |
| `opt-level = "z"` for the release profile | 347 840 B | −30 096 |
| the attribute table's error displayed, not `expect`ed | 341 136 B | −6 704 |
| the standard library's source path remapped | 340 992 B | −144 |

The image is now 340 992 B of 401 408 B: 60 416 B, 59 KiB, free. The
console image is 116 696 B.

`"z"` makes the code slower by an amount not measured here: it inlines
less and leaves loops rolled. The node logs its slowest step as
`longest_handle_us` in the 10 s line; one bench run against a `"s"`
image settles it. The largest stack frames grow by up to 2.4 KB (the
main task's poll 5 072 → 7 456 B, the phone link's 6 136 → 7 872 B,
by `llvm-objdump`), inside the 41.7 KB stack; `stack_used` in the same
line shows the result. RAM is unchanged.

The remap is for the image's bytes, not its size: generic code from
the standard library named its source under the toolchain's install
path, so an image built under another home directory differed.

## Recommended next, in order

1. Check `longest_handle_us` and `stack_used` on one board with the
   `"z"` image.
2. `HOME` and the USB logger out of `.data`: −4 192 B, no behaviour
   change, two small edits in `mailbox.rs` and `main.rs`.
3. The log lines that format large enums with `{:?}`: the trace line
   (up to −3 104 B) and the BLE errors (the host's and the
   controller's `Debug`, 2.9 KB of code and 1.9 KB of names) as codes
   or short names. A change to the log's format, so the bench's reading
   of it changes with it.
4. The host's packet pool, 4 036 B of `.data`, by a pool of our own
   built at boot instead of the host's default one.
5. If pairing and what follows still do not fit: halve the mailbox's
   ring (+16 384 B) before lending the update's pages (+45 056 B).

Without touching the layout or the toolchain, about 64 to 68 KB; the
layout adds 16 or 45 KB. The nightly flags would add about 28 KB more
by dropping panic locations, at the cost of the field's only diagnostic.

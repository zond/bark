# Pairing the phone link: can the node do it? (2026-11-06)

**Status:** measured on the host, 2026-11-06, against `df91ecf`: the BLE
host can pair with a passkey shown on the node and keep a bond, but the
image with pairing did not fit its slot. The same day the image went to
`opt-level = "z"` (`docs/flash-2026-11-06.md`), and pairing was built
(roadmap D135) with the host's central pairing cut, the last section.

## The question

Open item O23 asks for the phone link to be secured before nodes leave
the bench: LE Secure Connections pairing with a six-digit passkey shown
on the node's display and typed into the phone (passkey entry, Bluetooth
Core Specification Vol 3 Part H §2.3.5.6.3), bonded to one phone, every
characteristic but what the advertisement already says closed to a
connection that is not bonded. Before building it: does the BLE host the
firmware uses support this, and does the image still fit?

## What the host offers

The firmware's BLE host is TrouBLE, `trouble-host` 0.8.0, over Nordic's
SoftDevice Controller, `nrf-sdc` 0.4.0 (`bark-fw/Cargo.toml`). Its
`security` feature has everything the design needs, read in its source:

- LE Secure Connections pairing as a peripheral, with the I/O
  capability set to display only (`StackBuilder::set_io_capabilities`);
  the host draws a random passkey and hands it up as a
  `PassKeyDisplay` connection event, which the node would draw on the
  e-paper.
- Bonding per connection (`Connection::set_bondable`), the bond handed
  up in `PairingComplete` to be kept in flash and given back at boot
  (`StackBuilder::add_bond_information`); a `BondLost` event when a
  bonded phone pairs anew; an `Encrypted` event when a bonded phone
  comes back.
- A security level per characteristic:
  `#[characteristic(..., permissions(authenticated))]` answers a read,
  write or subscription on a link that is not encrypted with an
  authenticated key with ATT's Insufficient Authentication
  (`attribute.rs`, `AttPermissions`), which is the error a phone takes
  as its cue to pair (Vol 3 Part F §3.4.1.1).
- A phone's resolvable private address is resolved in the host with the
  identity key the phone gives when it bonds (`Identity::match_address`).
  The host also keeps the controller's resolving list up to date; the
  controller is built today without the privacy feature
  (`ble.rs`, `controller`), and whether that update then fails, and
  restarts the host, is not checked: `support_le_privacy()` may be
  needed.

The controller encrypts the link (the `LE Long Term Key Request Reply`
and `LE Enable Encryption` commands are in `nrf-sdc`). So the stack is
not a blocker.

## The cost

The firmware was built (`cargo build --release`, the node image without
a place) with the `security` feature added and nothing else changed, its
flash region widened only for the measurement, and the image's end read
by `scripts/uf2.py`. The running slot is 401 408 B (98 pages,
`bark-fw/README.md` "Flash layout"). None of these images holds the
firmware's own pairing code yet (drawing the passkey, keeping the bond,
the screen's paired word), likely 2 to 4 KB.

| Build | Image | Against the slot |
|---|---|---|
| today, `opt-level = "s"` | 377 936 B | 23 472 B free |
| + `security`, P-256 in Rust (`p256` crate) | 443 712 B | 42 304 B over |
| + `security-p256-cortex-m4`, P-256 in assembly | 433 832 B | 32 424 B over |
| + `security`, central pairing cut from the host | 435 952 B | 34 544 B over |
| today, `opt-level = "z"` | 347 904 B | 53 504 B free |
| `"z"`, + `security` | 407 296 B | 5 888 B over |
| `"z"`, + `security`, central pairing cut | 401 256 B | 152 B free |
| `"z"`, + `security-p256-cortex-m4`, central pairing cut | 396 704 B | 4 704 B free |

Where the 64 KB of the second row goes, by symbol: the host's own code
grows by 33 KB, most of it the pairing state machine, which compiles the
central's side too though the firmware is only a peripheral (cutting it,
by a local copy of the crate, saved 7.8 KB); the futures that join the
host's tasks by 5.6 KB; P-256 and its curve arithmetic 10 KB; AES and
CMAC 3.4 KB; the random generator the host seeds from the controller
2.6 KB. Static RAM grows by 1.8 KB, with the host's default room for ten
bonds; the stack, which has 41.7 KB, was not measured.

The assembly P-256 (`p256-cortex-m4`) is C and assembly built by the C
compiler: the build then needs `arm-none-eabi-gcc`, or clang with a C
library's headers, neither of which the build needs today. The rows
above used clang with a three-line `string.h`.

**Hardware crypto.** The nRF52840's CryptoCell-310 does P-256 and
AES-CMAC (Product Specification, CRYPTOCELL), but only through Nordic's
closed `nrf_cc310` libraries, which nothing in the build wraps, and the
host's crypto is fixed software with no hook to replace it. The
controller offers AES-128 in the ECB peripheral (`LE Encrypt`) but not
the P-256 commands (`LE Read Local P-256 Public Key`, `LE Generate
DHKey`): its header lists their bits in the supported-commands map and
declares no function for them. Hardware crypto would in any case save
at most the 10 to 17 KB of the crypto rows, not the 33 KB of the host's
code.

## Where room could come from

Each page more in the running slot costs two, since the staged slot is
one page larger than the running one (`bark-image/src/layout.rs`).

1. **`opt-level = "z"`** saves 30 KB on today's image. It trades speed
   for size in every crate, the core's relay and the drivers too; the
   radio's timing is in the SX1262 and the controller's in its own
   library, but how much slower the core's steps get would have to be
   measured on the bench. With it alone, pairing is 5.9 KB over.
2. **Cutting the central's pairing from the host** (a copy of the crate
   kept like the radio driver's, `vendor/`) saves 7.8 KB at `"s"`,
   about 6 KB at `"z"`. With 1, it fits by 152 B, before the
   firmware's own pairing code.
3. **Pages from the mailbox's ring.** Its 16 pages hold 256 items
   (`docs/app-layer-2026-11-05.md`, section 5). Four pages fewer give
   the slot two pages, 8 KiB, and leave 192 items. With 1 and the Rust
   P-256, that fits with 2.3 KB for the pairing code; with 1 and 2,
   with 8.3 KB.
4. **The assembly P-256** saves 5 to 10 KB more, at the price of a C
   compiler in the build.

Pairing at today's `"s"` would need 11 more pages in the slot, 22 in
all, more than the whole mailbox.

## What I would do

1, 2 and 3. `"z"` is a measured 30 KB that every later feature needs
too, with the image at 94 % of its slot today; 1 and 3 alone leave
2.3 KB for 2 to 4 KB of pairing code, so the host's central pairing
goes as well, kept as a copy like the radio driver. 1 first goes to the
bench alone, to see that the node keeps its timing; then pairing is
built with the ring at 12 pages. The C toolchain is not worth 5 KB.

## What was done

The image moved to `"z"` for every crate (`243548d`), 340 992 B. With
pairing on and the firmware's own code for it, the image was 4 664 B
over the slot, as the table's row for `"z"` foretold once that code was
added. So the host is a copy with its central's pairing behind the host's
`central` feature (`bark-fw/vendor/README.md`), and the image is
396 864 B, 4 544 B free. The controller is built with LE privacy
(`support_le_privacy()`), since the host puts a bonded phone's identity
key in its resolving list; it cost 16 B. The mailbox's ring keeps its 16
pages, and the build needs no C compiler.
